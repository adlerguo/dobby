# 数据备份与恢复说明

> 面向客户运维与实施。私有化部署下，数据安全由客户环境的备份策略保障。

## 1. 需要备份的数据

| 数据 | 存储 | 重要性 | 说明 |
|---|---|---|---|
| 业务与配置数据 | PostgreSQL | 极高 | 用户、角色、智能体、知识库元数据、发布、审计、评测等 |
| 向量数据 | PostgreSQL（向量扩展） | 高 | 知识库检索基础，重建成本高 |
| 文档原件 | 对象存储（MinIO） | 高 | 上传的原始文档 |
| 缓存 | Redis | 低 | 限流计数、临时状态，可重建，无需长期备份 |
| 加密主密钥/令牌密钥 | 部署配置/密钥托管 | 极高 | **丢失将导致已加密模型渠道无法解密** |

## 2. 备份策略建议

- **数据库**：每日全量 + 定期增量；异地保留。向量数据随库一起备份。
- **对象存储**：定期备份文档桶，或启用存储层冗余。
- **密钥**：加密主密钥与 JWT 密钥单独、安全托管，与数据库备份分开保存。**密钥不可与数据一起丢失。**
- 备份文件加密存储，定期做恢复演练。

## 3. 恢复流程（概要）

1. 恢复数据库（含向量数据）到目标环境。
2. 恢复对象存储文档桶。
3. **恢复原加密主密钥**——必须是加密时那一份，否则模型渠道密钥无法解密，需重新接入所有模型。
4. 启动服务，登录验证：智能体、知识库、模型渠道、发布应用是否正常。
5. 抽样做一次带引用的问答，确认知识库检索可用。

## 4. 关键提醒

- **密钥丢失 = 已加密渠道全部失效**。密钥备份优先级等同于数据本身。
- 换向量模型或重大升级前，先备份。
- 恢复演练每季度至少一次，验证备份可用。

## 5. 责任边界

平台提供数据结构与可备份的存储；实际备份计划、执行、异地容灾由客户运维负责。交付时双方明确备份责任与频率。
